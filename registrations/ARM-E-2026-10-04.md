## What Arm E Measures

Corollary 3.4 (`cor:model-update`, `sections/results.tex`) covers a model update applied from the episode start. It assumes the baseline policy is deterministic given its decision input and a random tape, and that inputs, tapes, and baseline outputs are recorded. If the new policy is seed-addressable, the agreement mass $\mathsf m_\kappa(r)=P^\kappa(\mathsf A_\kappa\mid r)$ is identified. It is estimated by the empirical agreement frequency over independent baseline episodes, and it is at most the first-decision agreement probability. Assumption (R) asks that the old and new kernels be known and deterministic in the declared input, which may include a recorded random tape. Part (vi) of the corollary's appendix statement warns that comparing only part of the output, such as the tool call without what later steps read, can break the identity.

Implementation (`experiments/agent-risk-harness/deltaai/arm-e/`):

- **Decision input.** The input at step $k$ is the request payload Inspect logged, sent with only the model name replaced. It holds the chat context, the 7 tool definitions, `tool_choice` auto, seed $=$ episode seed $\times 1000 + k$, temperature 0.7, top_p 1.0, and max_tokens 4096. Both sources were run with `log_model_api=True`, so every request was logged and none was rebuilt.
- **Independence of steps.** Agreement after step $k$ is judged at the logged input of step $k+1$, so the decisions of an episode are independent requests. The statistics stop each episode at its first disagreement; the later steps are kept as a diagnostic (unconditional step agreement).
- **Interfaces** (`arm_e_common.py`).
  - *Full interface*, the output later kernels read. It covers the text content and any reasoning text, plus the ordered tool calls with arguments parsed from JSON, key order kept. Text the server did not return counts as an empty string, as Inspect stores it; no model returned reasoning text. Whitespace inside an argument string is excluded for three reasons. vLLM parses the string into an object before the chat template re-serializes it (`vllm/entrypoints/chat_utils.py`, line 2153). Inspect hands parsed arguments to the monitor and the tools. No template of the four models renders tool-call ids, which vLLM draws at random.
  - *Action-only*: tool names and arguments compared as objects; text ignored.
  - *Raw* (all exact) and *full_ws* (content whitespace stripped) are diagnostics. On every rung and source they gave the same masses and first-decision rates as the full interface.
  - A context-length rejection by the server (3 logged decisions: 2 in `bi_baseline`, 1 in `c1_baseline`) is a decision. It agrees only with the same rejection.
- **Statistics** (`arm_e_analyze.py`). Each episode has a first-disagreement step per interface. The agreement mass is the share of episodes without a disagreement, and the first-decision rate the share whose first decision agrees. For the hazards, $N_k$ episodes agree through step $k-1$, $A_k$ of them make decision $k$ (the others have ended), and $D_k$ disagree at step $k$. The record reports the per-decision agreement $1-D_k/A_k$ and the clock agreement $1-D_k/N_k$; the product of the clock agreements over $k$ equals the agreement mass. Intervals are exact Clopper-Pearson 95% intervals and 95% percentile intervals from 10,000 episode-level bootstrap resamples. The bootstrap interval collapses to a point at $0/n$ and $n/n$, so the exact interval is the one to quote there.

## Seed Coupling

vLLM 0.30.0 samples a seeded request by the exponential race (`v1/sample/ops/topk_topp_sampler.py`, `random_sample`). A per-request `torch.Generator`, seeded with the request seed, fills that request's row of a float32 tensor of the logits width with exponential noise $q$. The token is $\arg\max_i p_i/q_i$, a Gumbel-max draw. `noise_check.py` (job 3304448) reproduced that call on a GH200 for 3 seeds and 8 consecutive decode steps:

| Comparison | Result |
|---|---|
| Width 151,936, seeded row at batch position 0 vs 3 | identical |
| Width 152,064 vs 151,936, on the first 151,936 indices | identical (fraction equal 1.0) |
| Width 248,320 vs 151,936, on the first 151,936 indices | identical (fraction equal 1.0) |

This is the behavior of PyTorch's grid-stride kernel when every element gets its own Philox subsequence, which holds for widths up to $256\times8\times132=270{,}336$ on a 132-SM GPU. The kernel then advances the generator by 4 per call, the same step vLLM rewinds for partial prefills (`gpu_model_runner.py`, `gen.set_offset(gen.get_offset() - 4)`). This mechanism is my reading of the kernels; the table is the measurement. Whether aligned noise means aligned tokens depends on the tokenizers (`vocab_check.py`):

| Model | Vocabulary entries | Ids naming the same string as in Qwen3-14B-FP8 |
|---|---|---|
| Qwen3-14B (bf16) | 151,669 | 151,669 of 151,669 |
| Qwen2.5-14B-Instruct | 151,665 | 151,665 of 151,665 (Qwen3 adds 4 tokens) |
| Qwen3.5-27B-FP8 | 248,070 | 281 of 151,669 |

Rungs 1, 2, and 4 therefore share the Gumbel noise of each decode position over one vocabulary, a common-noise coupling. Rung 3 shares noise by index while the indices name different strings, an arbitrary coupling. The setup record expected aligned noise only for equal vocabulary sizes; the measurement shows alignment across all three widths, which makes rung 4 aligned as well. Corollary 3.4 needs deterministic evaluation at the logged input and tape, not an aligned coupling. The coupling changes the value of the agreement mass, not its identification.

## What Each Rung Means for Corollary 3.4 and (R)

**Rung 1 establishes the corollary's hypotheses for these logs.** The logged policy, Qwen3-14B-FP8 served as the log was served, is deterministic given its decision input and tape. It is also reproducible on another GPU model: 1,650 of 1,650 decisions, logged on an H100, were reproduced on a GH200. The identity update has agreement mass 1, as it must, and the estimator returned no false disagreement. (R) holds for the logged agent at both serving modes. Batch-invariant kernels make it hold at concurrency 32; default kernels make it hold only at concurrency 1. No serving-numerics failure of (R) appeared on this rung.

**Rung 1k shows that the kernel in (R) includes the serving stack.** The same checkpoint in the other kernel mode reproduces the first decision in 7 of 99 episodes and the whole episode in 2. A change of kernels with fixed weights is therefore already a model update in the sense of the corollary. A log is replayable only together with a record of the serving mode, and the default mode at concurrency above 1 fails (R) outright (B0).

**Rungs 2 to 4 give the agreement mass for real updates, and it is near zero.** The new policies were evaluated deterministically at logged inputs and tapes, rung 3 with the per-process caveat below. The corollary therefore identifies the agreement mass, and the empirical frequency estimates it. At the full interface the first decision alone caps it at 0.086 for the precision-only update and at 0.037 for the release and the rollback, all at 95% confidence. Seed-addressable replay therefore identifies at most 9 percent of the episode law under the precision-only update, and at most 4 percent under the release or the rollback. The rest needs supported continuation (Proposition `prop:supported`), bounds, or new execution. This holds even with a common-noise coupling (rungs 2 and 4): aligned Gumbel noise does not keep a long sampled decision intact when the logits move.

**Rung 3 also tests seed-addressability itself.** Condition (M3) of the corollary's full statement asks that the serving stack rerun the new model at a logged context and seed and return the same output every time. On vLLM 0.30.0 the hybrid Qwen3.5 architecture meets this within a server process but not across processes, under each of the three Gated DeltaNet prefill backends. Each of the six rung 3 processes is a deterministic new kernel, and the estimate pools six slightly different ones. The paper's warning that sampling access is not seed-addressable has a finer version here: even a seeded open-weight server is seed-addressable only for a fixed process unless its kernels are deterministic. For this rung the caveat does not change the estimate, because agreement with the log was invariant across the six processes on every probe step.

**Interface.** Part (vi) of the corollary predicts that a partial comparison can break the agreement identity. The data show the mechanism: the releases write text the logged agent did not, the text is part of every later input, and action-only comparison overstates step agreement by up to 5.6 times. The full interface is the one the identification uses.

## Deviations From the Plan, and Why

1. **B0 not used.** Its default-kernel serving at concurrency 32 is not deterministic given input and tape, which the corollary assumes, and it lacks raw requests after the fifth call (Logged Sources). The primary source is `bi_baseline`.
2. **Rung 3 served with default kernels, one request at a time, in six shards.** vLLM 0.30.0 refuses `VLLM_BATCH_INVARIANT=1` for this model ("VLLM batch_invariant mode is not supported for GDN_ATTN"). The job script tried batch-invariant mode first and fell back as designed (`kernel_mode.txt` in each task directory). One request at a time keeps prefill chunking fixed per request; it does not remove the per-process numerics shown above.
3. **Rung 1k added.** The rung 1 job also replayed each source in the other kernel mode, at no extra queue cost. For `bi_baseline` this pass stopped each episode at its first action-only disagreement (127 decisions sent), which is enough for both interfaces' masses, first-decision rates, and hazards. Its by-length rates cover only the steps it evaluated.
4. **Noise check rerun as its own job.** The check inside the rung 1 job failed because the container call lacked the `/work/nvme/<ACCOUNT_SECONDARY>` bind; the script is fixed, and job 3304448 ran it.
5. **Rung 1 ran in `ghx4-interactive`.** At submission, `sbatch --test-only` predicted a 2.5-hour wait in `ghx4` behind a 24-node job, and `ghx4-interactive` started at once. That partition bills twice the GPU rate (billing 2000 per GPU). The other jobs, queued in `ghx4`, started within 3 minutes regardless.
6. **Replay engine sizing.** Replay servers used `--gpu-memory-utilization 0.85` (the log used 0.55 on an 80 GB H100). This changes only the KV cache size. No preemption occurred except 2 on rung 4 (Replay Setup).
7. **Gated DeltaNet diagnostic added** (job 3304657, 0.95 GPU-hours) after the rung 3 probe showed cross-process divergence; see Determinism Checks. A rung 3 rerun with the Triton backend was prepared and dropped when the diagnostic showed that backend is not reproducible across processes either.
8. **Shutdown messages.** The vLLM process reported "Bus error (core dumped)" on SIGTERM at the end of rungs 1 and 4, after all replies had been written and the metrics read. No core file was written.

## Open Issues

- Seed-addressability of hybrid releases. Qwen3.5-27B-FP8 on vLLM 0.30.0 is reproducible within a server process but not across processes, under every Gated DeltaNet prefill backend. Replaying rung 3 in one long-lived process would give an estimate for a single well-defined new kernel. That rerun takes about 1.5 GPU-hours and was not run, because agreement with the log did not depend on the process at any probe step and every first decision already disagreed. Making the kernel reproducible across processes, for example by pinning the autotuned configurations of the Gated DeltaNet kernels, would be an engineering fix like batch-invariant serving in rung 1; it was not attempted.
- The cross-model hazards after step 1 rest on at most 7 episodes. Estimating per-step hazards under a model update needs a task family whose first decisions are short. More episodes of this family would mostly add first-step failures.
- Rung 4 had 2 preemptions on a batch-invariant server; preemption recomputes a request's cache, and whether batch-invariant mode makes that recomputation exact was not tested. The bound in Replay Setup covers the effect on the reported counts.
- The H100 to GH200 reproduction holds for this model and these two serving modes. Other architectures were not tested across GPU models.
